# 데이터 질의 에이전트 (text-to-SQL)

[![CI](https://github.com/minkyong2927/sql-agent/actions/workflows/ci.yml/badge.svg)](https://github.com/minkyong2927/sql-agent/actions/workflows/ci.yml)

통신·렌탈 가입 중개 서비스의 운영 데이터를 말로 물으면, Claude가 SQL을 짜서 실행하고 결과를 근거로 답하는 에이전트.

**시연**: https://sql-agent-g25d.onrender.com (접속 코드 필요, 요청 시 전달 · Haiku 5.5 · 무료 서버라 첫 접속 시 1분 정도 대기)

```
질문: 사은품 지급 지연된 건 몇 건이고 총 얼마야?
  → Claude: run_sql 도구로 SELECT ... FROM gift_payouts WHERE status = '지연'
  → 실행 결과: 67 | 21630000
답변: 사은품 지급이 지연된 건은 67건, 총 21,630,000원입니다.
```

## 구성

| 파일 | 역할 |
|---|---|
| `schema.py` / `seed.py` | DuckDB 테이블 11개 생성 + 가상 데이터 생성 (고객 2,000명, 상담 2,514건, 가입 1,137건 등, 시드 고정) |
| `agent.py` | Claude API tool use 에이전트. 직접 구현한 루프, SQL 오류 시 모델이 스스로 수정, 실행 횟수·결과 크기 제한 |
| `guard.py` | sqlglot 기반 SQL 검사: 한 문장·조회문만, 금지 명령 차단, 테이블 허용 목록(파일 읽기 차단), LIMIT 강제 |
| `questions.py` | 평가 문항 40개 + 정답 SQL (쉬움 8 · 보통 10 · 어려움 12 · 함정 10) |
| `eval.py` | 평가 실행기: 답변 정답 / SQL 결과 정답 2종 채점, 병렬 실행, 문항별 결과·대화 기록 저장 |
| `rag.py` / `knowledge/` | 사내 문서 검색(RAG): 지표 정의서·운영 규칙·사은품 정책 4개 문서를 소제목 단위 19조각으로 색인, 벡터(임베딩)+BM25 하이브리드 검색 |
| `questions_knowledge.py` | 사내 용어 문항 12개 + 정답 SQL (정의가 문서에만 있음), 검색 점검용 바꿔 말한 질문 8개 |
| `router.py` | 난이도 분류 → 모델·사고량·SQL 실행 한도 배정, 실패 시 Opus 승급 |
| `judge.py` | LLM 채점기 (Sonnet 5.5): 핵심 값 일치 + 결론 명확성 판정, 알려진 정답·오답 162건으로 채점기 자체 검증 |
| `app.py` | FastAPI 서버 (`POST /ask`, 스트리밍 `POST /ask/stream`(SSE), `GET /health`, 시연 화면 `/`), 요청마다 JSON 로그 한 줄 |
| `repeat.py` | 반복 측정: 같은 평가를 N번 돌려 평균·표준편차·문항별 안정성, 두 설정 차이의 부트스트랩 95% 구간 |
| `label.py` | 사람 채점 대조: 실제 답변 40건을 블라인드로 직접 채점 → LLM 채점기·규칙 채점과 일치율·코헨 카파 |
| `pricing.py` / `log_report.py` | 토큰→비용 계산(평가·서버 공용) / 서버 로그 집계(응답 시간 p50·p95, 비용, 오류율) |
| `test_*.py` | 안전장치 15건, API·로그·스트리밍 31건, 승급 판단 7건, 통계 계산 6건 테스트 (API 테스트는 AI 호출을 가짜로 바꿔 무료) |
| `Dockerfile` / `render.yaml` | 컨테이너 이미지(빌드 시 DB 생성, 비root 실행) + Render 배포 설정 (접속 코드, IP당 시간 10회·하루 100회 제한) |

## 안전장치

1. **SQL 검사 (guard.py)**: `DELETE`·`DROP`·`COPY`·`ATTACH`·`SET` 등 차단, `SELECT 1; DROP ...` 끼워 넣기 차단, `read_csv('...')` 같은 로컬 파일 접근 차단
2. **DB 연결**: 읽기 전용 + 외부 접근 금지 (`enable_external_access=False`)
3. **실행 제한**: LIMIT 200 자동 부여, 모델에는 50줄까지, 질문당 SQL 8회까지

### LLM 채점 (judge.py)

규칙 채점은 정답 값이 답변 어딘가에 있으면 통과라서, 다른 값을 주 답으로 내세운 답도 통과시킴. 이를 보완하려고 평가 대상(Opus·Haiku)과 다른 모델(Sonnet 5.5)로 채점기를 추가함.

채점기 검증 (`python judge.py --calibrate`, 162건, $0.53):

| 넣은 답 | 기대 | LLM 채점 | 규칙 채점 |
|---|---|---|---|
| 정답 그대로 | 통과 | 40/40 | 40/40 |
| 다른 문항의 정답 | 실패 | 38/38 | 38/38 |
| 숫자만 바꾼 정답 | 실패 | 40/40 | 40/40 |
| 바꾼 값과 정답을 나란히 두고 고르지 않음 | 실패 | **38/38** | **0/38** |
| 빈 답 / "모르겠습니다" | 실패 | 6/6 | 6/6 |

저장된 실행 결과 다시 채점 (에이전트 재실행 없음, 약 $0.4):

| 실행 | 규칙 채점 | LLM 채점 | 갈린 문항 |
|---|---|---|---|
| Opus 기준선 | 30/30 | 30/30 | - |
| Opus v1 | 30/30 | 29/30 | 20번: 취소 제외 84건을 주 답으로, 정답 96건은 보조로 |
| Haiku v1 | 30/30 | 30/30 | - |
| Opus 함정 | 10/10 | 10/10 | - |
| Haiku 함정 | 10/10 | 8/10 | 32번: 793명을 주 답으로(정답 844명), 36번: 정답 72.3%를 낸 뒤 기간 맞춘 121.3%가 더 적절하다고 결론 |

- 20번("실제 가입까지 간 건")과 36번(10월 데이터가 25일까지만 있음)은 모델 해석에도 근거가 있음 → 모델 오류라기보다 **문항이 모호함**. 문항 문구를 고쳐야 할 대상
- 32·36번을 Haiku로 다시 돌리면 둘 다 통과 → 1회 실행 결과는 흔들림
- 문구 수정 (11-04): 20번 "가입 신청까지 간 건, 나중에 취소된 건도 포함", 36번 "10월은 데이터가 있는 날까지 쌓인 건수 그대로 비교" → Haiku 3회·Opus 1회 모두 규칙·LLM 채점 통과 (2문항 × 4회 = 8/8)

### 프롬프트 캐싱

도구 정의 + 시스템 프롬프트(스키마, 약 1,600토큰)는 모든 질문에서 같으므로 끝에 캐시 표시를 달고, 질문 안의 여러 차례 SQL 실행은 자동 캐시로 이어 붙임 (`agent.py`). 1~30번, 각 1회:

| 실행 | 입력 토큰 (일반 / 캐시 읽기 / 캐시 쓰기) | 비용 | 답변 정답 |
|---|---|---|---|
| Haiku, 캐싱 끔 | 109,198 / 0 / 0 | $0.019 | 29/30 |
| Haiku, 캐싱 켬 | 180 / 94,935 / 14,352 | **$0.011 (−42%)** | 29/30 (LLM 채점 30/30) |
| Opus, 캐싱 끔 (v1 실행) | — | $0.80 | 30/30 |
| Opus, 캐싱 켬 | 186 / 94,440 / 21,625 | **$0.48 (−40%)** | 29/30 (LLM 채점 29/30) |

- 입력의 약 87%가 캐시에서 읽힘. 남은 비용은 대부분 출력 토큰(Haiku 74%, Opus 73%)
- 정답 수 차이는 캐싱과 무관한 해석 차이: 10번은 두 모델 모두 취소를 뺀 분모(701건 중 208건)로 같은 비율 29.7%를 냄, 19번 Opus는 다른 기준 금액을 주 답으로 냄

### 난이도별 실행 예산 (router.py)

Haiku가 질문을 simple / complex로 분류하고, 난이도마다 예산을 다르게 줌. 예산 안에서 답을 못 내면(실행 한도 초과, SQL 전부 실패, 거절) Opus로 승급.

| 난이도 | 모델 | 사고량(effort) | SQL 실행 한도 |
|---|---|---|---|
| simple | Haiku | low | 3회 |
| complex | Haiku | medium | 6회 |
| 승급 | Opus | medium | 8회 |

40문항 전체, 캐싱 켬, 각 1회:

| 방식 | LLM 채점 | 규칙 채점 | 비용 | 문항당 시간 |
|---|---|---|---|---|
| Opus만 | 39/40 | — | $0.651 | 8.0초 |
| Haiku만 | 39/40 | — | $0.015 | 4.4초 |
| 난이도별 예산 (auto) | 40/40 | 38/40 | $0.019 | 6.3초 |
| 실패 시 승급 (cascade) | 40/40 | 39/40 | $0.016 | 4.1초 |

- 분류 결과: 쉬움 8/8 simple, 함정 10/10 complex, 보통·어려움은 섞임 (보통 3·어려움 2가 simple). 승급은 0건
- Opus만 쓰는 것보다 97% 싸지만, **Haiku만 쓰는 것보다는 비싸고 느림**. 분류 호출이 비용의 약 18%(토큰 차이로 추정), 시간 약 2초를 더함. 분류용 프롬프트는 캐시 최소 길이(512토큰)보다 짧아 캐싱도 안 됨
- 이 데이터에서는 Haiku가 이미 거의 다 맞혀서 분류로 아낄 몫이 작음 → 분류 없이 Haiku로 시작해 실패 신호가 있을 때만 승급하는 cascade(`--model cascade`)가 더 맞는 구조로 보임
- cascade 측정: auto보다 16% 싸고 2.2초 빠름, LLM 채점 40/40 유지. 승급 0건이라 사실상 Haiku 단독과 같은 비용·속도에 실패 시 안전망만 더한 구조. 규칙 채점 1건(Q10)은 비율 29.7%는 맞고 분모 해석(701 vs 761)만 다른 경우
- 승급 판단 규칙은 `test_router.py`로 API 없이 테스트 (CI 포함)

### 사내 문서 검색 (rag.py)

"골든타임 응대율", "청약철회", "사은품 SLA 위반"처럼 스키마만 봐서는 기준을 알 수 없는 사내 용어는 `knowledge/*.md`에만 정의가 있음. 이 정의를 찾아 에이전트에 넣는 구조

| 사내 용어 12문항 (cascade) | LLM 채점 | 비용 |
|---|---|---|
| 문서 없음 | 5/12 | $0.009 |
| 문서 전부 넣기 (19조각) | 12/12 | $0.007 |
| **검색 (hybrid)** | **12/12** | $0.007 |
| 검색 (bm25) | 12/12 | $0.005 |

- 문서 없이 틀린 이유: 골든타임을 1시간, 청약철회를 14일, 고액 사은품을 다른 금액으로 추측
- 문서가 19조각뿐이라 전부 넣어도 비용 차이는 작음. 검색은 문서가 늘어날 때를 대비한 구조이고, 아래 기존 40문항 결과처럼 관계없는 문서를 넣지 않는 것이 더 중요했음

**검색 방식 비교** (`python rag.py --eval`, API 호출 없음)

| 방식 | 사내 용어 문항 Recall@3 | 1순위 적중 | 바꿔 말한 질문 8개 |
|---|---|---|---|
| 벡터만 (potion-multilingual-128M) | 11/12 | 10/12 | 8/8 |
| BM25만 (한글 두 글자 단위) | 12/12 | 11/12 | 7/8 |
| **하이브리드 (코사인 + 0.1×BM25)** | **12/12** | **12/12** | **8/8** |

- 임베딩 모델 3개 비교: MiniLM(0.22GB) 1순위 3/12, mpnet(1GB) 8/12, potion(0.5GB) 10/12
- 벡터는 "하루도 안 돼서 취소" 같은 바꿔 말한 질문에, BM25는 "SLA", "ARPU" 같은 고유 용어에 강함. 질문에 용어가 통째로 들어 있으면 BM25 점수에 가산점(+5)

**검색 문서를 미리 붙였더니 기존 문항이 깨짐 → 구조 변경**

| 기존 40문항 (cascade) | LLM 채점 | 문항당 붙은 조각 |
|---|---|---|
| 문서 기능 없음 (이전 측정) | 40/40 | - |
| v1: 점수 0.8 이상 상위 3조각을 질문 앞에 붙임 | 36/40 | 2.2개 |
| v1 + "DB 값이 문서보다 우선" 규칙 | 39/40 | 2.3개 |
| **v2: 용어가 그대로 나온 조각만 붙이고, 나머지는 모델이 `search_docs` 도구로 검색** | **40/40** | 0.6개 |

- v1에서 "사은품 지급 지연"에 'SLA 위반' 문서가 붙어 status '지연' 대신 정책 기준으로 답함. 10번은 관계없는 문서 3개가 붙자 문서 없이 3/3이던 문항이 0/3
- 점수 기준을 올려도 바꿔 말한 질문의 정답 조각 점수가 관계없는 조각과 겹쳐 분리되지 않음 → "확실한 것만 미리, 나머지는 모델이 필요할 때 검색"으로 전환
- v2 사내 용어 12문항: 12/12 유지 (용어가 없는 "수도권", "응대 안 한"은 모델이 검색 도구로 찾음)

**메모리** (서버 프로세스, 문서 검색 1회 후)

| 방식 | 메모리 | 쓰는 곳 |
|---|---|---|
| bm25 | 136MB | Render 무료 (512MB) |
| hybrid | 약 690MB (mmap 없이 1,175MB) | 메모리를 늘릴 수 있는 환경 |

- 임베딩 표(0.5GB)는 mmap으로 질문에 나온 단어 줄만 읽음. 남은 메모리 대부분은 50만 단어 토크나이저
- 검색 1회 약 25ms. Docker 기본 빌드는 bm25(`--build-arg RAG_MODE=hybrid` 로 하이브리드 이미지)

### 반복 측정 (repeat.py)

1회 실행 점수는 실행마다 흔들려서 개선 효과를 말하기 어려움 → 같은 평가를 여러 번 돌려 편차를 보고, 두 설정의 차이는 문항을 다시 뽑는 부트스트랩으로 95% 구간을 냄

| 실행 (cascade, LLM 채점) | 회차별 | 평균 | 표준편차 | 회차마다 갈린 문항 |
|---|---|---|---|---|
| 사내 용어 12문항 · 문서 없음 × 5회 | 4, 5, 5, 5, 4 | 4.6/12 | 0.55 | 2 (ARPU 1/5, 완료 전환율 2/5) |
| 사내 용어 12문항 · 검색 × 5회 | 12, 12, 12, 12, 12 | 12.0/12 | 0 | 0 |
| 기존 40문항 · 검색 × 3회 | 40, 40, 40 | 40.0/40 | 0 | 0 |

- 문서 없음 → 검색: 문항당 통과율 +61.7%, 부트스트랩 95% 구간 [+36.7%, +86.7%] → 흔들림이 아닌 차이 (좋아진 문항 8, 나빠진 문항 0)
- 문서 없이 매번 틀린 6문항은 기준을 추측해야 하는 용어(골든타임, 청약철회, 장기 상담, 신입, 고액 사은품, SLA 위반)
- 1회 측정에서 흔들리던 기존 10번 문항도 v2 구조에서는 3회 모두 통과

### 사람 채점 대조 (label.py)

LLM 채점기 검증(162건)은 일부러 만든 오답 기준이라, 실제 에이전트 답변에서 사람 판단과 맞는지는 따로 잼. 위 반복 실행 답변 240건 중 40건을 뽑아(채점이 갈렸거나 실패한 답 20 + 나머지 20) LLM 판정을 가린 채 직접 채점

## 스트리밍 응답

`POST /ask/stream` 은 실행 과정을 SSE(text/event-stream)로 바로바로 보냄: `docs`(붙인 문서) → `search`(문서 검색) → `sql`(SQL 실행 결과) → `text`(답변 글자 조각) → `done`(최종 답변·토큰). 시연 화면이 이 경로를 씀

| 질문 (Haiku, 로컬) | 첫 SQL 결과 | 답변 첫 글자 | 완료 |
|---|---|---|---|
| 청약철회는 몇 건이야? | 2.95초 | 4.38초 | 4.80초 |
| 통신사별 인터넷 가입 건수 | 3.34초 | 4.44초 | 5.14초 |

- 에이전트 루프를 이벤트를 내보내는 생성기(`agent.run`)로 바꾸고, 기존 `ask()`는 그 결과를 모으는 함수로 둠 → 평가·일반 API와 스트리밍이 같은 코드
- 접속 코드·횟수 제한 거절은 스트림을 열기 전에 일반 오류(401·429)로 응답, 실행 중 API 오류는 `error` 이벤트
- 로그에 첫 글자까지 걸린 시간(`first_text_s`)을 함께 남김

## 운영 로그

`/ask` 요청마다 stdout에 JSON 한 줄. 거절(401·429)과 실패(502)도 남김. 응답 헤더 `X-Request-ID`와 같은 번호라 오류 신고가 오면 해당 줄을 바로 찾음

```
{"ts": "2026-11-04T13:36:48+0900", "event": "ask", "request_id": "544d6bb3a6c0", "ip": "846488f1dc",
 "question": "통신사별 인터넷 가입 건수", "model": "claude-haiku-5-5", "stop_reason": "end_turn",
 "n_sql": 1, "n_sql_error": 0, "input_tokens": 6, "output_tokens": 659, "cache_read_tokens": 3152,
 "cache_write_tokens": 544, "cost_usd": 0.00043, "status": 200, "latency_s": 5.28}
```

- IP는 원문 대신 해시 10자리, 질문은 200자까지
- `python log_report.py 로그파일`: Render 로그를 받아 요청 수·상태별 건수·응답 시간 p50/p95·비용·SQL 오류율·느린 요청 3건 집계
- 평가(eval.py)와 서버가 같은 `pricing.py`로 비용을 계산 → 오프라인 측정값과 운영 비용을 같은 기준으로 비교

## 실행

```
python -m venv venv
venv\Scripts\activate
python -m pip install -r requirements.txt
python -m pip install -r requirements-rag.txt   # 하이브리드 검색(임베딩)까지 쓸 때
```

`.env` 파일에 `ANTHROPIC_API_KEY=...` 를 넣은 뒤:

```
python schema.py && python seed.py      # DB 생성
python agent.py "질문"                   # 터미널에서 질문
python eval.py --check                  # 채점기 점검 (무료)
python eval.py --model claude-haiku-5-5 # 평가 실행
python eval.py --judge                  # LLM 채점까지 함께
python judge.py --calibrate             # LLM 채점기 검증
python eval.py --model auto             # 난이도별 실행 예산
python eval.py --model cascade          # 실패 시에만 Opus 승급
python rag.py --eval                    # 문서 검색 적중률 (무료)
python eval.py --model cascade --set knowledge --knowledge none   # 사내 용어 문항, 문서 없이
python repeat.py --set knowledge --knowledge none --n 5            # 반복 측정
python repeat.py --compare runs/<A> runs/<B>                       # 두 반복 실행 비교 (무료)
python label.py                         # 사람 채점 (labels/sample.jsonl 40건)
python label.py --report                # 사람 vs LLM 채점기 일치율
python log_report.py logs.txt           # 서버 로그 집계
uvicorn app:app --reload                # http://127.0.0.1:8000
```

## 한계

- 규칙 채점은 다른 기준의 숫자를 앞세운 답도 통과시킴 → LLM 채점으로 보완했으나, LLM 채점기 검증은 합성 오답 기준이라 사람이 직접 라벨링한 실제 답변으로 일치율을 재야 함
- 평가 문항이 이 데이터 기준으로는 쉬워 Opus·Haiku 간 차이가 드러나지 않음 → 다중 턴 질문, 정제되지 않은 데이터 문항 필요
- 사내 문서는 4개·19조각이라 검색 없이 전부 넣어도 동작함. 문서 수백 개 규모에서의 검색 품질·비용은 따로 재야 함
- 사내 용어 문항·문서·바꿔 말한 질문은 직접 만든 것이라 검색 설정이 이 문항에 맞춰졌을 수 있음
- 모든 결과는 1회 실행 기준 (10번처럼 해석이 갈리는 문항은 실행마다 달라짐)
